## Saved course basis and limits

Saved **Ep28** (S2): after any emotional spike the trader runs a reboot and then asks *“Am I calm? Am I clear? Am I following the trade plan? Would I take this trade if I was already up big today? If the answer to any of these questions is no, then you don't trade yet”*, with the rationale *“if you don't name the state, the state will control the trade.”* The repository already prescribed the rule **verbatim as advice** (`coach.js:311`) and already captured the input (the M89 entry-emotion text), but **not one of the four questions existed anywhere in `src/`** and nothing enforced the rule. See `EPISODE-AUDIT.md`; no new fetch, invented timestamp or full unavailable transcript.

The recorded answers are the trader's **own self-report**, not verified calmness, clarity, plan adherence, broker state, mental state or an edge. A gate pass is not a readiness/mental-state score, a percentage, a discipline grade, a dial or any authority over risk, admission, cap, routine, core or grades. The check is a **fresh in-session** check: it cannot be borrowed from yesterday, from a note, from profit or from adherence, and `M64`'s morning routine `check_in`, M89's timed entry/exit emotion capture and M107's daily intention stay separate mechanisms. The app's 60-minute/same-UTC-day freshness window is **APP policy**, not a quoted course timezone, session or trader/broker hours.

## Implemented mechanisms

1. **Owned immutable answer series.** Additive `state_gate_answers`: append-only, `human_declared` first-party rows and `imported_unverified` archives, with the original clock retained as history. SQL UPDATE facts immutable (FK nullification the only exception); owner deletion cascades, account deletion SET NULL retains the row for the owner's own readonly history and never re-attaches it to a foreign account. Not sealed against a database administrator. Nothing is backfilled from notes, profit, adherence or legacy journal text, and no answer is ever defaulted.
2. **Strict answer contract and CAS.** `PUT /state-gate` accepts **only** `{answers, revision}` where `answers` is exactly `{calm, clear, following_plan, would_take_if_up_big}` as a complete boolean set or explicit `null`; partial, extra, non-boolean or coerced input is `state_gate_invalid`. No caller clock, source, owner, score, text or override is accepted. The displayed 64-hex `revision` is a compare-and-swap: a stale value answers 409 with nothing written, an identical retry preserves the receipt/version, and an actual store failure answers 503 claiming no receipt and rolling back the new row only.
3. **Freshness and state model.** `not_adopted` (reported as adoption, never as a pass and **not blocked** — the app does not invent a check the trader never gave) / `passed` (fresh all-yes) / `failed` / `unanswered` / `stale` (>60 min or a different UTC day, inclusive edge) / `unavailable` (corrupt or future receipt). `allowed` is true only for a fresh all-yes pass; imported copies are `imported_unverified` archives that can never grant, refuse or block anything on the receiving account.
4. **Refusal parity with the killzone/personal stop.** A recorded no publishes `state_gate_failed` and appends a `status:'stop'` breach; missing/stale/unreadable is `state_gate_unanswered|stale|unavailable`. The gate folds into the guardrail snapshot and is consumed exactly like the existing personal stops: `Guards.applyToSetups`/Now refuse the candidate, `saveSignals`/`savePlan` answer with the gate's own 409 code, and `POST /trades` live entries plus `PUT /trades/:id` reopen answer 409 + a `state_gate` payload with **no financial row written**. Closing, editing, importing, and `record_only` journal history are never gated — an in-session check cannot hold a trader's history hostage.
5. **Desk resolution instead of an escape hatch.** `stateGateRefusal` answers `not_consulted` when there is no user, resolves an omitted account id to the trader's default unarchived desk, and answers `not_consulted` for an unowned desk or an invalid account so research and the existing guardrails stay the authority. A real adopted-but-not-fresh check refuses like a recorded no. The pre-hardening stage's 404 escape is measured and fixed (§ below).
6. **Actual daily surfaces.** Shared four-question card/editor on the Dashboard, the owned Journal day and Settings: the saved questions, the recorded answers, the current state text, `age_minutes`/`expires_at`, the APP window, the failed questions and an explicit `broker_verified:false`. Escaped text, no active HTML, no chart/provider fetch, no score/percentage/readiness/dial rendering. A failed gate shows the trader's own no and the way back rather than hiding it.
7. **Inherited emotion requirement kept, not re-invented.** The ledger row's “require `emotion_before`” clause was already enforced on the app's own prospective surface by the M89-era `J.text(body.emotion_before, 'Name your emotional state before prospective entry')`: a blank/absent named state is refused 400 **before** the gate is consulted, on both the new-entry and reopen paths. M106 asserts that pairing; `record_only` history with an empty `emotion_before` still records exactly as before.
8. **Scope and budgets.** Answer history, history reads and its own JSON backup/restore; unchanged100-char single-line emotion text,20MB selected-file/25MB request limits, trade CSV untouched. No new meditation/progress mechanism (M108 partial), no daily intention field (M107), no strategy/risk/goal/grade/core/admission/routine write.
